# 작성 코칭 — 채팅 팁과 작성 가이드

초안을 넘길 때 "여기서 무엇을 고려하고 무엇을 더 적어야 하는지"를 함께 준다. 기준은 아래 세 가지다.

1. **PSST 작성법** — 저자 원문 [PSST 프롬프트 마스터](https://github.com/jhsoo0211/bussiness-planner-skills/blob/182e45a113ae4945cf3b5cd4eae61dfab3993dde/docs/psst.md)의 섹션별 출력 항목. 원문은 저장소 `docs/`에만 있고 설치본에는 없으므로, 섹션별 항목을 아래 3절 체크리스트로 옮겨 두었다(실행 때 웹 접속 불필요).
2. **심사 성향** — `bizplan-review/references/judge-insights.md` §4(J). [의견]·[사용자 노하우]는 공식 기준이 아니라고 밝힌다.
3. **사례 체크포인트** — `bizplan-review/references/case-insights.md`(C).

## 1. 두 가지 전달 방식

| 방식 | 언제 | 무엇을 |
|------|------|--------|
| **채팅 작성 팁** | 섹션 하나를 보여줄 때마다(모든 작성 모드) | 섹션 끝에 3~4줄 — ① 작성법 기준 ② 이 초안에서 디벨롭할 곳 ③ 다음 행동. 보강 제안 블록 바로 앞에 둔다 |
| **작성 가이드** `작성가이드.md` | 파일 모드에서 초안이 완성됐을 때(빠른 버전 끝, 꼼꼼 버전 검토 뒤), 사용자가 "어디를 어떻게 고쳐야 하는지" 물을 때 | 사업계획서와 **따로 보는 산출물**. 사업계획서 목차 순서대로 "그 부분은 ~를 고려해야 한다 / ~를 적어야 한다"를 정리한다. 본문을 복사하지 않고, 사업계획서 파일에는 아무것도 끼우지 않는다 |

채팅 팁 예:

> **작성 팁** — 작성법은 Pain Point마다 *발생 빈도·심각도*와 *해결되지 않을 때의 손실*을 요구한다. 이 초안의 P1·P2는 둘 다 비어 있고 "(팀 가설)"이다. 다음 행동: 20~30대 30명에게 "필터 고르는 데 몇 초 쓰나, 다시 보정한 적이 있나"를 묻고 숫자 두 개를 P1 첫 줄에 넣는다.

## 2. 작성 가이드 만드는 법

1. `bizplan/scripts/guide_draft.py 사업계획서.md --review 검토리포트.md --out 작성가이드.md`로 골격을 만든다. 사업계획서 목차(소제목)마다 절이 하나씩 생긴다. 스크립트가 미리 채우는 칸은 다음과 같다.
   - 작성법 항목의 있음·없음 자동 판정
   - 그 절의 미확보·가설 표기 → "~를 채워야 한다"·"~를 확인해야 한다" 항목
   - 작성법 항목 → "~를 적어야 한다" 체크 항목
   - 검토 리포트의 점수 영향(△·X를 O로 바꾸면 오르는 점수)
   - 절별로 부탁할 자산(아래 3절 표)
2. ✍ 칸을 이 초안을 읽고 채운다. 자동 판정은 단어로 짐작한 것이니 본문을 읽고 ✓·△·✗로 고친다. 남은 ✍가 0개가 될 때까지 채운다.
3. 맨 앞 '한눈에'에 다음 세 가지를 쓴다.
   - 지금 점수와 목표
   - 점수가 가장 많이 오르는 행동 3개(기한·점수 영향·반영할 목차)
   - 모아 주실 자료(스크립트가 목차별로 모아 둔다 — 이 아이템에 맞게 고친다)
4. 맨 끝 '제출 전 체크리스트'는 그대로 두고, 빈칸 수만 확인한다.

목차별 절 형식(고정):

```markdown
### 2-2. 고객 Pain Point

**지금 상태**: 작성법 ✓ Pain Point 3개 · ✗ 발생 빈도·심각도 · △ 손실 / P1·P2가 '팀 가설' / 점수 영향 문제 인식 '근거 수치·출처' △→O +3점

**고려해야 할 점**

- 직접 근거(인터뷰·관찰)가 통계 인용보다 강하다는 점을 고려해야 한다 — 자체 설문만이면 약하다(C 1)
- P2는 '앱 사용자에게만 해결'이라는 범위를 그대로 밝혀야 한다

**꼭 적어야 할 것**

- [ ] Pain Point마다 발생 빈도와 심각도를 적어야 한다(작성법 SPIN-P)
- [ ] 해결되지 않을 때 손실을 적어야 한다(작성법 SPIN-I)

**이렇게 써 보세요** *(사실을 확인한 뒤 ○○를 채운다)*

> **P1** — 사진 1장당 필터 선택에 평균 ○○초, ○○%는 결국 늘 쓰던 필터로 돌아간다(20~30대 ○○명 관찰, 2026.○○).

**발표에서는**

- 인터뷰 인용 하나로 시작해 빈도 숫자로 잇는다

**근거 확보** *(무엇을 · 어떻게 · 언제)*

- 인터뷰 10문항 + 화면 녹화 관찰 5명 — M1~M2(브리프 12장과 같게)

**있으면 넣어 주세요**

- 고객 인터뷰 메모·녹취 요약(표)
- 설문 결과(응답 수·기간)
```

규칙:

- 문장은 **"~를 고려해야 한다", "~를 적어야 한다", "~를 바꿔야 한다"**로 끝내 할 일이 바로 보이게 한다.
- **이 초안의 내용을 집어서** 말한다(절 번호·문장 인용). 어느 계획서에나 붙는 일반론은 쓰지 않는다. 잘 쓴 부분은 "유지해야 한다"고 적어 고치지 않게 한다.
- 초안 문장은 사실이 없으면 ○○ 자리로 둔다. 숫자·기관명·실적을 지어 넣지 않는다. 쓸 수 있는 조건(예: "LOI를 받았을 때만")을 붙인다.
- 표현 수위는 증빙 단계에 맞춘다(J §4 협력 단계: 인터뷰 완료 < 협의 진행 < MOU 협의 중 < MOU 체결 < 공동 수행 실적).
- 점수 영향은 검토 리포트의 하위 항목 판정에서만 계산한다(△→O = 배점의 50%, X→O = 100%). 검토 전이면 "검토 후 계산"으로 둔다. 행동 3개의 합계는 실제로 더해 맞춘다.
- **있으면 넣어 주세요**는 이 절을 강하게 만들 **사용자 쪽 자산**(이미 만든 결과물·증빙·자료)을 구체적으로 부탁하는 칸이다. 무엇을(예: 앱 화면 캡처 3장), 어떤 형태로(사진·표·링크) 줄지 쓴다. 없는 자산을 있는 것처럼 쓰지 않는다. 받으면 사업계획서의 [작성 필요]를 사실로 바꾼다.
- 공통 규칙(마스킹·미확보 표기·기본값)을 그대로 따른다. 저자 원문의 'S대' 이니셜 표기는 공통 규칙의 ○○ 마스킹으로 대신한다. 자산에 실명·학교명·로고가 있으면 블라인드 규칙대로 가려서 넣는다.
- 작성 가이드는 **제출하지 않는다**. 제출본은 `사업계획서.md`(와 변환본)다. 사용자가 원하면 `md_to_docx.py`·`md_to_hwpx.py`로 따로 변환해 준다.

## 3. 섹션별 작성법 체크리스트 (PSST 작성법 + J·C)

`guide_draft.py`가 이 표의 항목을 목차별 절에 넣는다. 항목을 바꾸면 스크립트의 `CHECKS`도 같이 바꾼다.

| 절(소제목 신호) | 작성법 항목 (docs/psst.md) | 심사 관점 (J·C) |
|------------------|----------------------------|------------------|
| 개요·요약 | 아이템명 공식 "[어떤 기술]이 적용된, [어떤 기능]의 혜택을 제공하는, [어떤 제품/서비스]" · 사업 범주 · 핵심 요약 5줄(문제·솔루션·타겟·차별점·BM) 각 1줄 | 10초 안에 문제 실재성·해결 대응·실행 증거가 보이는가(C 「가장 먼저 보는 것」 1·2·3·9) |
| 시장 배경·배경 및 필요성 | 시장 배경을 구체적 수치·출처와 함께 · SPIN의 상황(S): 고객이 처한 상황과 통용되는 방식 | 거시 통계만 있고 우리 고객의 고통으로 좁히지 못하면 약하다(C 문제인식) |
| 고객 Pain Point·문제 | Pain Point 3개 · 발생 빈도와 심각도 · 해결되지 않을 때 손실(시간·비용·기회비용 / 사회적) · 실제 사례·인용·통계 | 직접 근거(인터뷰·민원·관찰)가 통계 인용보다 강하다(C 1) · 자체 설문만이면 약하다 |
| 기존 솔루션의 한계·경쟁 | 한계 2개 이상 · 경쟁사가 해결하지 못한 점 명시 · 경쟁사 비교표(회사명·주력 제품·타겟·가격대·강점·약점·점유율) · 차별화(기능·가격·서비스·기술) · 경쟁 우위 확보 방안 3 | 경쟁사 한계를 우리가 어떻게 해소하는지까지(review 체크포인트 4) · 실명 비교 |
| 필요성·왜 지금 | 필요성 2개 · 해결 시 이점(Need-payoff) · 니즈 증거(시장 성장률·유사 솔루션 성공 사례·인터뷰/설문) · 정부지원사업비로 해결할 핵심 기능 명시 | 규제 변화·정책·시장 변화와 연결한 타이밍(C 문제인식 잘 쓴 패턴) |
| 타겟 고객·시장 현황 | 1차·2차 타겟(연령대·직업·소득·특징·Pain·구매 동기) · 페르소나 2명 · 시장 규모 표(국내·글로벌, 연도별, CAGR) · 세분화 · 니즈 3 · 트렌드 3 · 모든 데이터 출처 | 세분화가 측정·접근·구매력·니즈 동질성 기준으로 타당한가(review 체크포인트 9) |
| 실행 증거·현황(준비 정도) | 시제품·MVP·데모, 사용자·매출 지표, LOI·MOU·PoC, 수상·언론·웹/SNS(현재까지 한 일) | 만든 것은 링크·캡처로 문서에 실물로, 없으면 협약기간 내 제작 일정으로(C 3·9) |
| 핵심 기능·기술 구현 | 핵심 기술 3개(구현 난이도·확보 방안) · 기술 리스크 2개와 대응 · 기능마다 푸는 문제 | 성능 정량치·제3자 검증 경로 · 분야 필수 인증·규제(C 실현가능성) |
| 개발·추진 일정 | 월차별 주요 활동·세부 내용·산출물·예산 · 마일스톤(2개월·5개월·8개월 무렵) · 협약일 기준 | 이미 검증된 것과 앞으로 확인할 것을 구분(author-insights solution) |
| 사업비·예산 | 비목 표(세부 내용·금액·비율) · 1단계·2단계 구분 · 항목별 산출 근거 | 산출 근거(단가 × 수량·견적) · 합계 검산(check_tables) · 공고 비목 기준 |
| 비즈니스 모델·수익 | 주요 수익원·과금 방식·예상 객단가 · 비용 구조(고정비·변동비) · BM 캔버스 9블록 · 가격 전략(초기·프리미엄·책정 근거) · BM 구성도(가치 흐름·수익 흐름·파트너·비용) | 매출 가정을 채널·판매량·단가·전환율로 분해(C 가장 먼저 보는 것 8) |
| 시장 규모·TAM | (시장 현황 표와 같음) | TAM→SAM→SOM으로 좁히고 층위마다 산식·출처 · 가장 큰 경쟁자 벤치마킹 · SOM 200억 권장선은 예창패 노하우(공식 기준 아님, U300 완화)(J §4) |
| 마케팅·시장 진입 | 초기 고객 확보(0~6개월) 전략 2 · 성장기(6~12개월) 전략 2 | 범용 계획(홈페이지·SNS·인플루언서)은 감점 — 접촉 완료·견적·예산·기대성과 수준으로(J §4) |
| 단·중·장기 목표 | 목표·전략·핵심 지표 표(1년·2~3년·5년) · 확장 계획(제품·시장·파트너십) | 시장진입 계획 뒤에 비전을 잇는다(비전 생략 금지)(J §4) |
| SWOT | 강점·약점·기회·위협 각 3 · 교차 전략(SO·WO·ST·WT) | 약점을 숨기지 않고 WO·WT로 보완 경로를 보인다 |
| 대표자 역량 | 관련 경력 2 · 핵심 역량 3 · 창업 동기(진정성) | 스펙 나열이 아니라 핵심 리스크를 맡을 수 있는가(J §4, C 팀 구성) |
| 팀 현황 | 구분·담당 업무·보유 역량·확정/예정 표 | 리스크 ↔ 담당자 매핑 · 공백은 확보 계획으로 |
| 협력 기관 | 기관명·협력 내용·협력 시기·기대 효과 표 | 협력 단계를 증빙 범위 안에서 최상위 격식 표현으로(J §4) |

## 4. 작성 가이드 '한눈에' 형식

```markdown
## 한눈에
| 지금 | 목표 | 가장 큰 공백 |
|------|------|--------------|
| ○○점(가정 배점) · 빈칸 ○곳 · 가설 ○곳 | 과락선 ○○점 이상 | (예: 팀 역량, 1차 근거) |

**점수가 가장 많이 오르는 행동 3개**
1. (행동) — (기한) — (점수 영향) — (반영할 목차)

**모아 주실 자료** *(있는 것만 — 받으면 반영할 목차)*
- [ ] (자산) → (목차)
```

그 뒤에 `## 목차별 가이드`(2절 형식, 사업계획서 목차 순서)와 `## 제출 전 체크리스트`(빈칸 0 · 출처 원문 대조 · 검산 · 양식 안내 문구 삭제 · 블라인드 · 협력 표현 단계 · 대응표 일치)가 온다.
