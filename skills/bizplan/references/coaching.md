# 작성 코칭 — 채팅 팁과 작성 가이드

초안을 넘길 때 "여기서 무엇을 고려하고 무엇을 더 적어야 하는지"를 함께 준다. 기준은 아래 세 가지다.

1. **PSST 작성법** — 저자 원문 [PSST 프롬프트 마스터](https://github.com/jhsoo0211/bussiness-planner-skills/blob/182e45a113ae4945cf3b5cd4eae61dfab3993dde/docs/psst.md)의 섹션별 출력 항목. 원문은 저장소 `docs/`에만 있고 설치본에는 없으므로, 섹션별 항목을 아래 3절 체크리스트로 옮겨 두었다(실행 때 웹 접속 불필요).
2. **심사 성향** — `bizplan-review/references/judge-insights.md` §4(J). [의견]·[사용자 노하우]는 공식 기준이 아니라고 밝힌다.
3. **사례 체크포인트** — `bizplan-review/references/case-insights.md`(C).

## 1. 두 가지 전달 방식

| 방식 | 언제 | 무엇을 |
|------|------|--------|
| **채팅 작성 팁** | 섹션 하나를 보여줄 때마다(모든 작성 모드) | 섹션 끝에 3~4줄 — ① 작성법 기준 ② 이 초안에서 디벨롭할 곳 ③ 다음 행동. 보강 제안 블록 바로 앞에 둔다 |
| **작성 가이드** `작성가이드.md` | 파일 모드에서 초안이 완성됐을 때(빠른 버전 끝, 꼼꼼 버전 검토 뒤), 사용자가 "어디를 어떻게 고쳐야 하는지" 물을 때 | 사업계획서와 **따로 보는 산출물**. 사업계획서 목차 순서대로 "그 부분은 ~를 고려해야 한다 / ~를 적어야 한다"를 정리한다. 본문을 복사하지 않고, 사업계획서 파일에는 아무것도 끼우지 않는다 |

채팅 팁 예:

> **작성 팁** — 작성법은 Pain Point마다 *발생 빈도·심각도*와 *해결되지 않을 때의 손실*을 요구한다. 이 초안의 P1·P2는 둘 다 비어 있고 "(팀 가설)"이다. 다음 행동: 20~30대 30명에게 "필터 고르는 데 몇 초 쓰나, 다시 보정한 적이 있나"를 묻고 숫자 두 개를 P1 첫 줄에 넣는다.

## 2. 작성 가이드 만드는 법

1. `bizplan/scripts/guide_draft.py 사업계획서.md --out 작성가이드.md [--brief 브리프.md] [--review 검토리포트.md]`로 골격을 만든다(검토 리포트가 있을 때만 `--review`). 사업계획서 목차(소제목)마다 절이 하나씩 생긴다. 스크립트가 미리 채우는 칸은 다음과 같다.
   - 작성법 항목의 있음·없음 자동 판정
   - 그 절의 미확보·가설 표기 → "~를 채워야 한다"·"~를 확인해야 한다" 항목
   - 작성법 항목 → "~를 적어야 한다" 체크 항목
   - 검토 리포트의 점수 영향(△·X를 O로 바꾸면 오르는 점수)
   - 절별로 부탁할 자산(아래 3절 표)
2. ✍ 칸을 이 초안을 읽고 채운다. 자동 판정은 단어로 짐작한 것이니 본문을 읽고 ✓·△·✗로 고친다. 남은 ✍가 0개가 될 때까지 채운다.
3. 맨 앞 '한눈에'에 다음 세 가지를 쓴다.
   - 지금 점수와 목표
   - 점수가 가장 많이 오르는 행동 3개(기한·점수 영향·반영할 목차)
   - 모아 주실 자료(스크립트가 목차별로 모아 둔다 — 이 아이템에 맞게 고친다)
4. 맨 끝 '제출 전 체크리스트'는 그대로 두고, 빈칸 수만 확인한다.

목차별 절 형식(고정):

```markdown
### 2-2. 고객 Pain Point

**지금 상태**: 작성법 ✓ Pain Point 3개 · ✗ 발생 빈도·심각도 · △ 손실 / P1·P2가 '팀 가설' / 점수 영향 문제 인식 '근거 수치·출처' △→O +3점

**고려해야 할 점**

- 직접 근거(인터뷰·관찰)가 통계 인용보다 강하다는 점을 고려해야 한다 — 자체 설문만이면 약하다(C 1)
- P2는 '앱 사용자에게만 해결'이라는 범위를 그대로 밝혀야 한다

**꼭 적어야 할 것**

- [ ] Pain Point마다 발생 빈도와 심각도를 적어야 한다(작성법 SPIN-P)
- [ ] 해결되지 않을 때 손실을 적어야 한다(작성법 SPIN-I)

**이렇게 써 보세요** *(사실을 확인한 뒤 ○○를 채운다)*

> **P1** — 사진 1장당 필터 선택에 평균 ○○초, ○○%는 결국 늘 쓰던 필터로 돌아간다(20~30대 ○○명 관찰, 2026.○○).

**발표에서는**

- 인터뷰 인용 하나로 시작해 빈도 숫자로 잇는다

**근거 확보** *(무엇을 · 어떻게 · 언제)*

- 인터뷰 10문항 + 화면 녹화 관찰 5명 — M1~M2(브리프 12장과 같게)

**있으면 넣어 주세요**

- 고객 인터뷰 메모·녹취 요약(표)
- 설문 결과(응답 수·기간)
```

규칙:

- 문장은 **"~를 고려해야 한다", "~를 적어야 한다", "~를 바꿔야 한다"**로 끝내 할 일이 바로 보이게 한다.
- **이 초안의 내용을 집어서** 말한다(절 번호·문장 인용). 어느 계획서에나 붙는 일반론은 쓰지 않는다. 잘 쓴 부분은 "유지해야 한다"고 적어 고치지 않게 한다.
- 초안 문장은 사실이 없으면 ○○ 자리로 둔다. 숫자·기관명·실적을 지어 넣지 않는다. 쓸 수 있는 조건(예: "LOI를 받았을 때만")을 붙인다.
- 표현 수위는 증빙 단계에 맞춘다(J §4 협력 단계: 인터뷰 완료 < 협의 진행 < MOU 협의 중 < MOU 체결 < 공동 수행 실적).
- 점수 영향은 검토 리포트의 하위 항목 판정에서만 계산한다(△→O = 배점의 50%, X→O = 100%). 검토 전이면 "검토 후 계산"으로 둔다. 행동 3개의 합계는 실제로 더해 맞춘다.
- **있으면 넣어 주세요**는 이 절을 강하게 만들 **사용자 쪽 자산**(이미 만든 결과물·증빙·자료)을 구체적으로 부탁하는 칸이다. 무엇을(예: 앱 화면 캡처 3장), 어떤 형태로(사진·표·링크) 줄지 쓴다. 없는 자산을 있는 것처럼 쓰지 않는다. 받으면 사업계획서의 [작성 필요]를 사실로 바꾼다.
- 공통 규칙(마스킹·미확보 표기·기본값)을 그대로 따른다. 저자 원문의 'S대' 이니셜 표기는 공통 규칙의 ○○ 마스킹으로 대신한다. 자산에 실명·학교명·로고가 있으면 블라인드 규칙대로 가려서 넣는다.
- 작성 가이드는 **제출하지 않는다**. 제출본은 `사업계획서.md`(와 변환본)다. 사용자가 원하면 `md_to_docx.py`·`md_to_hwpx.py`로 따로 변환해 준다.

## 3. 섹션별 작성법 체크리스트 (PSST 작성법 + 섹션 설계도 + J·C)

`guide_draft.py`의 `CHECKS`가 이 표의 원본이다(이 표는 그 목록에서 만든다). 항목을 바꿀 때는 스크립트의 `CHECKS`를 먼저 고치고 이 표를 다시 만든다. 절마다 주장형 헤드라인 수와 시각자료 수도 함께 센다(섹션 설계도 1-1·3절).

| 절 | 작성법 항목 (PSST 작성법 + 섹션 설계도) | 심사 관점 |
|----|------------------------------------------|-----------|
| 개요·요약 | 한 줄 소개(타깃·측정 가능한 문제·해결 방식·결과물) · 아이템명 공식(기술이 적용된, 혜택을 제공하는, 제품/서비스) · 사업 범주 · PSST 요약(문제·실현·성장·팀) | 10초 안에 무엇을 하는 팀인지, 문제 실재성·해결 대응·실행 증거가 보이는가(B2, C 가장 먼저 보는 것 1·2·3·9) |
| 배경(내부·외부·왜 지금) | 대표·팀의 직접 경험(내부 배경) · 공적 통계 수치(외부 배경) · 출처 표기 · 왜 지금(제도·수요·기술 가격 중 하나) | 장면 → 확인 행동 → 확산 확인 → 왜 지금. 문제는 크게, 해법은 좁게(B3) |
| 문제 정의(필요성 n) | 문제 2~3개(우선순위) · 발생 빈도·심각도 · 손실 환산(시간·금액) · 현재 대처행동과 한계 · 직접 근거(인터뷰·관찰·인용) | 직접 근거(인터뷰·관찰·민원)가 통계 인용보다 강하다, 자체 설문만이면 약하다(B4, C 1) |
| 차별·경쟁 | 실명 비교 3곳 이상 · 대체재(고객의 현재 대처행동) · 자사가 불리한 축 · 확인 경로(URL·확인 시점) · 우위 유지 근거(관계·계약·축적 데이터) | 경쟁사 한계를 우리가 어떻게 해소하는지 + '경쟁사가 같은 기능을 붙이면 무엇이 남나'에 답하는가(B8) |
| 필요성·왜 지금 | 필요성 2개 · 해결 시 이점(Need-payoff) · 니즈 증거(성장률·성공 사례·인터뷰) · 지원사업비로 해결할 핵심 기능 | 규제·정책·시장 변화와 연결한 타이밍(C 문제인식) |
| 목표시장·고객 | 1차 고객 수(모집단 × 발생률 × 의향) · 결제자 기준 · 페르소나 카드(인용·검증 n/N) · 세분화 근거 | '모든 사람'은 고객이 아니다 — 측정·접근·구매력·니즈 동질성으로 좁혔는가(B5) |
| 준비 정도(실행 증거) | 보유역량(경험 횟수·기간·자산) · 진행역량(완료·진행·예정 상태) · 미확보 공개(되는 것·안 되는 것) · 실물 증빙(사진·화면·링크·별첨) | 만들어 실행한 것은 실물로(사진·링크), 없으면 확인 계획(언제·누구·무엇)으로(B6, C 3·9) |
| 구체화(솔루션 n)·기술 | 솔루션 n ↔ 문제 n 번호 · 고객 편익 수치(시간·비율·조건) · 기술 리스크와 대응 · 기술 보호·지재권 상태 | 기능 나열이 아니라 '문제 n을 이렇게 푼다'는 편익 중심, 동작 안 하는 기능은 계획으로(B7) |
| 로드맵·일정 | 월차·분기별 활동·산출물 · 마일스톤 · 인과(과업 → KPI → 매출) · 예산 연결 | 로드맵은 일정표가 아니라 '이 과업을 이 시점에 하기 때문에 이 매출'이 되는 인과 사슬(B13) |
| 사업비 | 비목 표(세부 내용·금액) · 비율 · 항목별 산출 근거(단가 × 수량) · 검산(합계 = 상한) | 산출 근거·합계 검산(check_tables)·공고 비목 기준(B9) |
| 비즈니스 모델 | 한 문장 공식(누구에게 무엇을 얼마에) · 매출 산식(대상 수 × 전환율 × 단가) · 단가 근거(지불 의향·경쟁가·절감분) · 결제자와 과금 방식 | 누가 무엇에 왜 지불하는가가 한눈에 — '사용자 먼저, 수익화는 나중'은 공백으로 읽힌다(B10) |
| 시장 규모(TAM·SAM·SOM) | TAM·SAM·SOM 층위 · 층위별 산식(상향식) · 1차 고객 수 · 출처 | 거대한 TAM보다 도달 가능한 1차 고객 수와 산출 근거가 먼저(B5). SOM 200억 권장선은 예창패 노하우(공식 기준 아님)(J §4) |
| 시장 진입 | 퍼널(단계 인원·구간 전환율) · 접촉 완료 수 · 채널별 방식·비용 | 채널명 나열이 아니라 접촉 대상·방식·완료 수 — 범용 홍보는 접촉·예산이 있을 때만(B11, J §4) |
| 매출·투자·고용(협약 기간 목표) | 매출(금액 + 산식) · 투자(LOI·조건 또는 미팅 진행) · 고용(포지션 × 시기) · 이후 3년·흑자 전환 조건 | 협약 기간 매출·투자·고용을 숫자로 — 수치는 사실·근거로만, 비전은 그 뒤에(B12, J §4) |
| SWOT | 강점·약점·기회·위협 · 교차 전략(SO·WO·ST·WT) | 약점을 숨기지 않고 WO·WT로 보완 경로를 보인다 |
| 대표자 | 당사자성(직접 겪거나 처리한 경험) · 관련 경력·전공 · 준비 행동(날짜순) · 적임자 한 문장 | 스펙 나열이 아니라 문제 ⇄ 역량 ⇄ 역할의 연결(B14, J §4, C 팀 구성) |
| 팀(R&R·보완) | R&R(책임 범위) · 상태(확보·예정·협의 중) · 보완 계획(시점·예산·검증) · 협업 구조 | 빈 분야를 먼저 본다 — 비어 있는데 계획이 없는 것만 감점(B14) |
| 협력 기관 | 기관·보유 역량·협력 내용 · 협력 시기(조건부 가능) · 단계(접촉 < 협의 < LOI < MOU < 실적) | 협력 단계를 증빙 범위 안에서 최상위 격식 표현으로(J §4 사다리) |

### 절별로 부탁할 자산 (있으면 넣어 주세요)

| 절 | 부탁할 자산 (형태) |
|----|-------------------|
| 개요·요약 | 대표 이미지(앱 화면·시제품 사진 1장), 서비스 로고·이름 |
| 배경(내부·외부·왜 지금) | 현장 사진(촬영일·장소·대상 수 캡션), 관련 기사·통계 원문 캡처 |
| 문제 정의(필요성 n) | 고객 인터뷰 메모·녹취 요약(표), 설문 결과(응답 수·기간), 불편 장면 사진·리뷰 캡처 |

## 4. 작성 가이드 '한눈에' 형식

```markdown
## 한눈에
| 지금 | 목표 | 가장 큰 공백 |
|------|------|--------------|
| ○○점(가정 배점) · 빈칸 ○곳 · 가설 ○곳 | 과락선 ○○점 이상 | (예: 팀 역량, 1차 근거) |

**점수가 가장 많이 오르는 행동 3개**
1. (행동) — (기한) — (점수 영향) — (반영할 목차)

**모아 주실 자료** *(있는 것만 — 받으면 반영할 목차)*
- [ ] (자산) → (목차)
```

그 뒤에 `## 목차별 가이드`(2절 형식, 사업계획서 목차 순서)와 `## 제출 전 체크리스트`(빈칸 0 · 출처 원문 대조 · 검산 · 양식 안내 문구 삭제 · 블라인드 · 협력 표현 단계 · 대응표 일치)가 온다.
