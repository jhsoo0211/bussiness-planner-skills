# 공통 규칙: 지원사업 성격 파악 (전 모드 공용)

모든 bizplan 모드는 작업 시작 전 이 파일을 읽고 아래를 확인한다. 이 파일이 공통 기준이며, 각 서브스킬에는 요약과 필요한 참조 연결을 둔다. 공통 정책·수치가 바뀌면 이 파일을 수정한다. 저자의 파트별 작성 노하우는 아래 적용 계약과 지정된 원문을 함께 따른다.

## 적용 범위와 실행 환경 (Claude Code · Codex 공통)

- 이 스킬군은 **한국 정부 창업지원사업의 PSST(Problem · Solution · Scale-up · Team) 사업계획서**를 중심으로 설계했으며 기본 안내는 한국어다. 영어 README는 설치·사용 설명의 번역이다. 다른 국가·유형의 문서에는 해당 양식·평가 기준을 먼저 확보해 조정한다.
- 스킬 경로는 현재 환경이 제공한 실제 설치 위치를 기준으로 해석한다. `references/`와 `scripts/`는 해당 `SKILL.md`가 있는 폴더 기준이며, 다른 모드의 공통 문서는 설치된 `bizplan/references/common-rules.md`를 읽는다. `~/.claude/skills` 같은 특정 환경 경로를 가정하지 않는다.
- 세부 모드를 실행할 때 그 스킬의 `SKILL.md`를 읽고 지침을 따른다. 전용 스킬 호출 도구가 없더라도 파일을 읽어 진행할 수 있다.
- 웹 검색·파일 생성·Python·문서 변환·시각 검수는 **현재 호스트가 제공하는 도구와 권한 범위**에서 수행한다. 도구가 없으면 요청 자료나 가능한 대체 산출물을 안내하고 미실행·미검증 범위를 명시한다. 도구 이름·호출 성공·실시간 출처 검증을 지어내지 않는다.
- 사용자·팀 제공 사실, 외부 확인 사실, 가정, 예시 수치를 구분한다. 미제공 매출·파트너십·인증·실험 결과를 사실로 채우지 않는다.
- Claude 전용 명령(`/cost` 등)을 Codex 명령으로 안내하지 않는다. 모델·사용량은 실행 중인 제품의 UI/보고값을 기준으로 하며 실제 측정이 없으면 추정 또는 알 수 없음으로 표시한다.

## 저자 작성 노하우 적용 (작성 전 필수)

`bizplan-item`·`bizplan-outline`·`bizplan-problem`·`bizplan-research`·`bizplan-solution`·`bizplan-growth`·`bizplan-team`·`bizplan-summary`·`bizplan-quick`은 **본문 작성 전에** 자신의 `SKILL.md`, 이 공통 규칙, [저자 작성 인사이트 적용 지도](author-insights.md)의 현재 모드 행과 거기 지정된 원문 절을 읽고 적용한다. **라우터를 거치지 않은 직접 호출에도 동일하다.** 이미 읽은 현재 판본은 재사용할 수 있으며 모든 참조를 무조건 읽을 필요는 없다.

- 공식 공고·평가표·양식의 항목과 분량을 우선한다. 저자 노하우는 그 안에서 근거 선택·문제와 해결의 연결·실행 계획을 강화하는 기준이다.
- 저자 노하우와 이번 프로젝트의 사실·가설을 구분한다. 기존 사례·예문의 수치, 팀 이력, 파트너십을 현재 팀의 사실로 가져오지 않는다. `[의견]`·`[추론]`·사용자 노하우의 적용 조건을 지우거나 공식 기준으로 바꾸지 않는다.
- 사용자가 지정한 핵심 문제와 우선순위·제약을 보존한다. 양식 순서가 달라도 문제와 해결의 인과 관계를 유지한다. 해결책이 부족한 핵심 문제는 삭제 대신 **미해결/추가 검증 필요/현재 범위 밖**으로 명시하고 후속 과제로 남긴다. 일부만 해결하면 효과와 처리 규모의 한계를 쓴다.
- 대응 점검은 문제·기능의 개수를 같게 만드는 검사가 아니다. 한 문제를 여러 기능이 함께 풀거나 한 기능이 여러 문제에 기여할 수 있다. 각 연결의 근거와 해결 범위를 설명한다. 작성·검토 모두 사용자가 동의하지 않은 방향·핵심 문제의 우선순위 변경을 자동 반영하지 않는다. 필요한 변경은 이유를 붙인 대안으로 제시한다.
- 작성 후 해당 모드의 기준이 실제 내용에 반영됐는지 점검한다. 내부 참조 약호·읽기 경로를 사업계획서 본문에 노출하지 않는다. 부족한 근거는 확인 사항·자료 요청·검증 계획으로 제시한다.
- 필수 참조가 없거나 읽을 수 없으면 실제 설치 위치를 확인한다. 끝내 접근할 수 없더라도 가능한 초안 작업은 이어가되, 적용하지 못한 작성 기준이 있음을 밝힌다. 한 줄 요약만 보고 원문 노하우 전체를 적용했다고 주장하지 않는다.

## 섹션 설계도 적용 (작성 전 필수)

본문을 쓰는 모든 모드는 [섹션 설계도](section-blueprints.md)(약호 **B**)의 블록 문법을 따른다. 요점은 다음과 같다.

- **블록과 양식 매핑**: 사업계획서를 블록 B1~B14로 쓰고, 공고 양식 목차에 배치한다(B 4절). 양식이 없으면 B 4-1 기본 목차를 쓴다.
- **헤드라인**: 소제목은 `○ [태그] 결론 문장`으로 쓴다. 숫자는 권장이고, 없으면 ○○ 자리를 둔다.
- **블록 순서**: 헤드라인 → 시각자료(제목에 결론 수치, 아래 출처·시점·표본) → 근거 2~4줄 → 출처·별첨·확인 경로.
- **문체는 양식별로 자동**(B 1-4)
  - 문서형: 헤드라인 + 개조식
  - 온라인 문항형: `◆ 소제목` + 짧은 서술 문단
  - 사용자가 지정하면 그것을 따른다.
- **번호 실**: 문제 n ↔ 솔루션 n ↔ 차별점 n ↔ 화면 라벨을 같은 번호로 잇는다.
- **숫자 등록부**: 핵심 숫자 6~10개를 `브리프.md`의 '숫자 등록부' 절에 먼저 적는다(값 · 의미 · 산식·출처·시점 · 근거 수준 · 들어갈 블록). 본문·개요·그림·발표는 이 값만 쓴다.
- **근거 수준 라벨**: 수치마다 확인 / 산출 / 관찰 / 가정을 단다. 조사·검토에서는 판정(그대로 사용 / 단서와 함께 / 재조사)을 단다.
- **보수 추정**: 의향·전환율·재구매율은 조사값의 절반을 쓰고 이유를 적는다. 산식은 곱셈을 그대로 보이고, 합계 표에는 검산 상자를 둔다.
- **실적이 없을 때**: 확인 계획 3요소(언제 · 누구 · 무엇)로 쓴다. 미확보 항목은 먼저 밝힌다.
- **시각자료**: 번호 절(1-1, 2-2 등)마다 1개 이상 슬롯을 둔다. 문서형 10쪽 기준 12~16개이고, 작성 시작 때 이미지 예산표를 만든다. 무엇을 세는지는 섹션 설계도 3-2.
- **3지표**: 성장 절에 매출·투자·고용 블록(B12)을 둔다. 수치는 사실·근거로만 쓴다.

## 도구 사용 (도구 지도 한 곳)

작업 중에 다른 스킬·도구(웹 조사, 데이터 검증, 차트, 문서 편집, 규제 확인 등)를 쓸 때는 [도구 지도](tool-map.md)의 해당 작업 행을 따른다.

- 환경에 그 스킬이 있으면 부르고, 결과를 bizplan 형식으로 받아 옮긴다. 없거나 실패하면 '없으면' 칸의 내장 절차로 한다.
- 스킬 목록이 보이지 않는 환경이면 `bizplan/scripts/find_tools.py`로 확인한다.
- 토큰이 많이 드는 작업(심층 웹 조사·병렬 조사)만 처음 한 번 묻는다.
- 산출물 끝 '보강 제안'에 사용한 도구를 한 줄로 적는다.

## 브리프 우선과 맥락 관리

대화가 길어지면 앞에서 받은 사실을 놓치거나 섞기 쉽다. 그래서 사실은 **`브리프.md` 한 파일**에 고정하고, 각 모드는 대화 기억이 아니라 이 파일을 근거로 작업한다.

- **브리프가 사실 원본이다.** 작업 폴더(또는 첨부)에 `브리프.md`가 있으면 모든 모드는 작성 전에 먼저 읽고, 거기 있는 것은 다시 묻지 않는다. 대화 내용과 브리프가 다르면 사용자에게 확인하고 브리프를 고친다.
- **새 사실·결정은 바로 브리프에 적는다** — 해당 칸과 '결정 기록', '진행 상황'을 갱신한다. 상태 표기([자료]/[진술]/[가정]/[미확보])를 지킨다.
- **브리프가 없을 때**: 라우터는 작성 전에 `bizplan-interview`로 보낸다(사용자가 원치 않으면 건너뛰되, 그 모드의 필수 문항은 묻는다). 모드가 바로 호출됐으면 "인터뷰부터 할까요, 바로 진행할까요?"를 한 번 묻고, 바로 진행이면 그 모드에 필요한 블록(`bizplan-interview/references/questions.md`)을 한 턴에 묻고 받은 답으로 간이 브리프를 만든다.
- **단계마다 새 대화가 기본이다(꼼꼼 버전)**: 큰 단계(인터뷰·큰틀·섹션 작성·검토·발표)가 끝나면 산출물을 파일로 저장하고, 다음 단계는 새 대화에서 `브리프.md` + 그 단계에 필요한 파일만 첨부해 시작하라고 안내한다(예: 검토 = 브리프 + 사업계획서.md). 토큰 절약뿐 아니라 **품질을 위한 기본 진행 방식**이다.
- **같은 대화에서 이어갈 때**도 각 파트를 쓰기 직전에 브리프의 해당 장을 다시 읽는다. 기억에 의존해 숫자·상태를 옮기지 않는다.
- **웹·앱(claude.ai)**: 브리프를 샌드박스 파일로 만들고, 인터뷰가 끝나면 내려받게 안내한다. 새 대화에는 그 파일을 첨부한다.

## 파악할 항목

1. **주관기관과 사업명**: 아래 '지원사업 프로필' 표의 사업 / 기타. 프로필의 양식 구조·강조점을 출발점으로 쓰고, 공고문을 받으면 공고가 우선한다.
2. **평가 기준·배점**: 공식 배점표가 있으면 반드시 첨부를 요청한다 — 배점 항목에 본문을 매핑하는 것이 점수의 지름길이다.
3. **지원 규모·기간·분량**: 해당 공고 기준으로 쓴다. 공고를 확인하지 못했으면 아래 '기본값과 기준 연도' 절을 따른다.
4. **양식 구조**: 예창패 PSST형 / 청창사 기술성·시장성·사업성형 / U300형 / 로컬크리에이터 지역성형 / 기타(프로필 표 참조)
5. **심사 방식**: 서면 / 발표. 발표 심사가 있으면 초안 완성 후 `bizplan-pitch`로 연결한다. 지정 발표 템플릿(.pptx)이 있으면 함께 받는다.

## 기본값과 기준 연도 (수치는 이 절에만 둔다)

지원 규모·기간·분량은 사업과 연도마다 바뀐다. 스킬 안의 수치는 **공고를 확인하기 전 초안용 기본값**이며, 다른 파일은 이 절을 참조만 한다. 평가 단계·항목·가점·양식 규정은 `bizplan-review/references/rubrics.md`에 사업별로 있다(아래 값과 같은 2026-10 조사, 확인 수준 표기).

| 사업 | 초안용 기본값 | 출처·상태 |
|------|---------------|-----------|
| 예비창업패키지 (2026) | 1단계 2,000만 원(협약 후 4개월 이내 집행) → 중간 평가로 50% 내외에 2단계 2,000만 원 내외 추가(평균 0.4억), 협약 8개월 이내, 사업계획서 목차 제외 10쪽 이내, 단계별 70점 미만 제외 | 2026 공고(제2026-143·207호) [원문 색인 발췌] — 원문 대조 전 |

- 공고를 확인하지 못한 값은 본문에 `[공고 확인 필요: 항목]`으로 남기고, 가정으로 진행한 값은 "가정"이라고 적는다. 공고의 실제 값을 받으면 전부 바꾼다.
- 분량(쪽수·글꼴·글자 크기)은 공고·양식 값을 쓴다. 공고를 못 받았으면 위 표와 `rubrics.md`의 해당 연도 값을 "(○○년 공고 기준, 확인 필요)"로 쓰고, 그것도 없으면 쪽수를 정하지 않고 비율로만 배분한다.

## 지원사업 프로필 (양식 구조·강조점 출발점)

자격·금액·분량은 해마다 바뀌므로 **이 표에는 넣지 않는다** — 공고에서 확인한다. 아래는 양식을 받기 전 구조를 잡는 출발점이다.

| 사업 | 대상(일반적) | 양식 구조 | 먼저 보여줄 것 |

## 정부지원사업이 아닌 경우

투자 유치 IR, 민간 공모전, 정책자금·대출 심사, 사내벤처, B2B 제안 등이면 해당 심사·평가 자료(IR 가이드라인, 공모 요강, 심사 항목표) 첨부를 요청한다. 자료가 없으면 유형별 부각 포인트를 먼저 안내한다:

- **IR** = 팀·시장·트랙션·유닛 이코노믹스·투자금 사용처(라운드·희망 밸류·엑싯 전략 포함)
- **공모전·경진대회** = 주최 취지 부합·창의성·발표 전달력 가중(재무·양산 계획 비중↓, 통상 5~10페이지 — **공공 주최는 지식재산 귀속·공공 활용 동의 조항이 있는 경우가 많으니 확인하도록 고지**)
- **정책자금·대출** = 상환 능력·재무 건전성
- **B2B 제안** = 고객사 문제 해결과 ROI

이후 각 모드의 출력 형식을 그 유형에 맞게 조정한다.

## 제출 양식 핏 (양식 파일 제공 시)

사용자가 제출 양식(공고 양식 hwp/hwpx/docx/pdf 파일, 목차 캡처, 항목표 텍스트)을 제공하면 **양식이 스킬 기본 구조보다 우선**한다. 모든 모드가 다음을 따른다:

1. **목차·순서 준수**: 산출물의 목차·항목명·항목 번호·순서를 양식 그대로 따르고, 각 산출물 헤더에 양식 항목 번호(예: 1-1, 2-2)를 표기한다.
2. **항목별 지시문·분량 준수**: 양식에 적힌 항목별 작성 지침·분량 제한(페이지·글자 수)을 지킨다. 양식의 안내 문구(예: 예창패 파란 안내 박스)는 제출 전 삭제 대상으로 표시한다.
3. **차이 처리**: 스킬 기본 구조에는 있으나 양식에 없는 내용은 가장 가까운 양식 항목에 병합하고, 양식에는 있으나 초안에 없는 항목은 "**[작성 필요: 항목명]**"으로 남겨 누락을 드러낸다.
4. **양식 읽기**: `bizplan/scripts/read_form.py 양식파일`로 본문·목차 후보·안내 문구(표 칸 포함)·분량 지시·표를 뽑는다(.hwp/.hwpx/.docx/.pdf — .hwp는 python-hwpx 필요). 도구가 없거나 배포용(암호화) 문서라 읽지 못하면 목차·항목 텍스트를 채팅에 붙여넣어 달라고 요청한다.

양식을 받기 전에 이미 만든 산출물이 있으면, 양식 확보 시점에 그 목차 기준으로 재배치한다.

## 연혁·보유 자산·활동 로그 반영 (제공 시)

사용자(팀)가 실제 이력·자산 자료를 제공하면 일반적인 서술 대신 **그 자료의 사실(날짜·수치·성과)을 근거로 작성**한다. 증빙 없는 일반론보다 실제 이력이 담긴 계획서가 심사에서 훨씬 유리하다.

- **대상 자료**: 연혁(창업·수상·제품 출시·투자 유치·계약·팀 합류 등 시간순 이력) / 팀 어셋(경력·포트폴리오·특허·인증·시제품) / 활동 로그(개발 일지·회의록·실험·실측 기록·고객 인터뷰·런칭 기록) / 증빙(MOU·LOI·매출 자료)
- **배치**: 연혁·팀 어셋은 팀 구성(대표자 이력·팀 연혁)에, 개발·실험 로그는 실현 가능성(개발 경과·검증 이력)에, 고객 인터뷰·매출 자료는 문제 인식·성장 전략에 우선 반영한다.
- **표기**: 출처를 "(팀 제공 자료)"로 표기하고, 제공 자료와 모순되는 내용을 만들지 않는다. 개인정보 마스킹 규칙은 그대로 적용한다.
- 세션에서 한 번(라우터 후속 질문 또는 각 모드 시작 시) 보유 여부를 확인하고, 이미 받은 자료는 다시 요청하지 않는다.

## 보강 제안·자료 요청 (산출물 공통)

본문을 생성하는 모든 모드(item·outline·problem·research·solution·growth·team·summary·quick·export)는 산출물 말미에 **"작성 팁"**(채팅, 아래 '작성 코칭' 절)과 **"보강 제안"** 블록을 붙인다:

1. **있으면 좋을 내용**: 이 섹션을 더 강하게 만들 추가 내용 제안(예: 연혁, 실측 데이터, 고객 인용, 파일럿 결과, 재구매율) — 각 항목에 심사 관점에서 왜 유리한지 한 줄 이유를 단다.
2. **요청 자료**: 사용자에게 요청할 자료 목록(공고문·배점표·제출 양식, 연혁·어셋·활동 로그, 구매의향서·시험성적서 등 증빙)을 우선순위와 함께 제시하고, 받으면 어느 항목에 반영할지 명시한다.
3. `bizplan-review`는 별도 블록 대신 기존 '약점 및 개선점'·'필수 수정'에 요청 자료를 연결해 제시한다.

## 작성 코칭 (채팅 팁 · 작성 가이드)

초안만 넘기지 않고 "여기서 무엇을 고려하고 무엇을 더 적어야 하는지"를 함께 준다. 기준과 형식은 [작성 코칭](coaching.md)에 있다.

- **채팅 작성 팁**: 섹션을 보여줄 때마다 끝에 3~4줄을 붙인다.
  - ① PSST 작성법(docs/psst.md)의 그 절 기준
  - ② 이 초안에서 디벨롭할 곳(절 번호·문장을 집어서)
  - ③ 다음 행동
  - 어느 계획서에나 붙는 일반론은 쓰지 않는다.
- **작성 가이드** `작성가이드.md`: 사업계획서와 **따로 보는 산출물**이다. 파일 모드에서 초안이 완성되면 만든다(빠른 버전 끝, 꼼꼼 버전 검토 뒤, 완성 문서 모드 빌드 뒤, "어디를 어떻게 고쳐야 해?"라고 물을 때).
  - `bizplan/scripts/guide_draft.py 사업계획서.md --out 작성가이드.md [--brief 브리프.md] [--review 검토리포트.md]`로 골격을 만든 뒤 ✍ 칸을 채운다. 사용자가 골격만 원하면 ✍ 칸을 남긴 채 넘기고 남은 줄 수를 알린다.
  - 사업계획서 목차 순서대로 절마다 지금 상태 · **고려해야 할 점** · **꼭 적어야 할 것**(체크 항목) · 이렇게 써 보세요 · 발표에서는 · 근거 확보 · **있으면 넣어 주세요**(사용자 자산 요청)를 쓴다. 문장은 "~를 고려해야 한다", "~를 적어야 한다"로 끝낸다.
  - 맨 앞 '한눈에'(점수가 가장 많이 오르는 행동 3개와 모아 주실 자료), 맨 끝 '제출 전 체크리스트'를 둔다.
- 사업계획서 본문에는 가이드 내용을 끼우지 않는다. 초안 문장은 사실이 없으면 ○○ 자리로 둔다. 작성 가이드는 제출하지 않는다(제출본은 `사업계획서.md`).

## 확인 방법

사용자가 모르면 공고문 파일을 요청하거나 웹 검색으로 파악한다. 대화에 이미 정보가 있으면 다시 묻지 않는다.

**공고문도 웹 검색도 없을 때**: 공고문 첨부를 한 번 요청하고 작업은 멈추지 않는다. 지원 규모·기간·배점·양식은 `[공고 확인 필요: 항목]`으로 두고, 진행에 필요한 값은 '기본값과 기준 연도' 절대로 "가정"이라고 밝혀 쓴다. 기관·회사 정보처럼 사실 확인이 필요한 내용은 "미검증"으로 표시해 사용자에게 넘긴다.

## U300 등 학생 트랙 — 깊이 인터뷰

학생 팀은 원가 데이터·시제품·매출 실적 같은 증빙 자산이 없는 경우가 많다. 예창패 수준의 깊이를 일괄 적용하지 말고, 아래 3~4가지로 **무엇을 갖고 있는지 항목별로** 먼저 확인한다.

① **원가·단가 데이터** — 견적서·BOM·재료비 계산이 있는가
② **시제품·실측·증빙** — 시제품(사진), 성능 실측치, 시험 결과, 1차 조사(설문·인터뷰)가 있는가
③ **매출·계약 실적** — 판매 이력, 구매의향서(LOI), PoC 협의가 있는가
④ (재무 추정을 쓸 계획이면) **추정 근거** — 고객 수·단가·전환율 가정을 세워 봤는가

**있는 항목은 예창패 수준 깊이로 쓰고, 없는 항목은 "산정 예정(근거·확보 시점 명시)" 폴백으로 처리한다**(`bizplan-solution` B-1 원칙). 전체를 일괄 간략화하지 않는다 — 항목별 판단이 원칙이다. 이 확인 결과는 이후 모드(`bizplan-solution`·`bizplan-research`·`bizplan-review`)가 재사용한다. 라우터를 거치지 않고 모드가 바로 호출됐다면 그 모드의 첫 질문 턴에 위 항목을 **한 문항으로 묶어**(예: "원가·시제품·실적·추정 근거 중 갖고 있는 것을 골라 주세요") 함께 묻는다 — 질문 턴을 늘리지 않는다.

## 출력 형식 (세션 공통)

세션에서 정한 형식(채팅 / .md / .docx / .hwpx)을 모든 모드가 따른다. 완성 문서 모드(`bizplan-document`)는 형식을 묻지 않고 .md · .docx · .hwpx · .pdf를 모두 만든다. 파일 모드면 결과를 파일에 누적하고 채팅에는 요약만 보여준다. 정해진 것이 없으면 채팅 출력을 기본으로 하되, 긴 문서면 파일 저장을 한 번 제안한다. 환경별 파일 처리는 `bizplan` SKILL.md의 '출력 형식 (세션 공통)' 절을 참조한다.

| 변환본 | `사업계획서.docx`·`.hwpx`·`검산표.xlsx` | 마지막에 만든다 |

- **.docx**: `bizplan/scripts/md_to_docx.py 사업계획서.md 사업계획서.docx [--gov-bullets]`(A4·한글 글꼴·표 테두리).
- **.hwpx/.hwp**: `bizplan/scripts/md_to_hwpx.py 사업계획서.md 사업계획서.hwpx [--hwp]`(python-hwpx 필요). 한컴오피스에서 1회 열어 확인하라고 안내한다. 공고 양식 파일의 칸을 채우는 것이 아니라 새 문서를 만든다.
- 최종 제출본은 공고가 지정한 양식이다. 변환본은 양식으로 옮기기 위한 초안이다.

### 제출본 표기 (양식별 문체)

- 문체는 섹션 설계도 1-4(양식별 자동)를 따른다. 아래는 문서형 제출본의 표기다.
- 제출용 변환본(.docx/.hwpx)과 사용자가 공문서 표기를 원할 때는 계층을 **□ → ○ → - → ·**로 쓰고, 문장 끝은 명사형(~함·~임·~음, 체언)으로 맺는다. 변환 스크립트의 `--gov-bullets`(hwpx는 기본)가 불릿 계층을 바꿔 준다.
- 채팅·.md 초안은 마크다운 불릿과 **굵게**를 기본으로 쓴다. 근거 줄의 어미는 섹션 설계도 1-4를 따른다(문서형은 .md에서도 명사형 개조식, 헤드라인은 `~다`). 양식이 다른 표기를 지정하면 양식을 따른다.

### 숫자 검산 (넘기기 전 필수)

예산·재무·시장 규모 표가 들어간 산출물은 넘기기 전에 `bizplan/scripts/check_tables.py 파일.md`로 합계·비율 100%·곱셈식을 검산한다. 오류는 고치고, '판단 보류'(단위 혼합 등)는 직접 확인한다. 사용자가 엑셀 검산표를 원하면 `--xlsx 검산표.xlsx`(합계 행 =SUM 수식).

### 스킬 스크립트 실행

- 스킬의 `scripts/`는 `python3 -B <설치 위치>/<스킬>/scripts/<이름>.py`로 실행하거나, import가 필요하면 `sys.path.insert(0, "<설치 위치>/<스킬>/scripts")` 후 `python3 -B`로 실행한다. 스킬 폴더에 캐시·결과 파일을 쓰지 않는다 — 결과는 작업 폴더에 둔다.
- 필요한 라이브러리(python-pptx·python-docx·python-hwpx·openpyxl·matplotlib)가 없으면 설치를 제안하고, 설치할 수 없으면 가능한 대체 산출물과 못 한 검증을 밝힌다.

### 참조 문서 갱신

`judge-insights.md`·`case-insights.md`·`award-patterns.md`·`visual-guide.md`에 새 내용을 더하라는 지시가 있어도, **설치본 스킬 폴더는 직접 고치지 않는다**(읽기 전용이거나 다음 설치 때 덮인다). 작업 폴더의 `bizplan-notes/<대상 파일명>`에 추가안을 쓰고, 사용자가 저장소에 반영하도록 안내한다. 사용자가 이 저장소 원본에서 작업 중이면 동의를 받아 원본을 고친다.

## 개인정보 마스킹

- 학교명·직장명 등 개인을 특정하는 정보는 **○○로 가린다**: '○○대학교 ○○학과 졸업', '○○전자 연구원 5년', '○○시청 담당자 인터뷰'. 'S대'·'K사' 같은 이니셜은 기관을 연상시켜 블라인드 취지에 어긋날 수 있으므로 쓰지 않는다.
- 예외: **제출 양식이 소속·실명 기재를 공식 요구하는 칸**(예: 학생창업 트랙의 소속대학, 재학증명)은 양식을 따른다. 그 칸 밖의 자율 서술은 마스킹한다.
- 발표 템플릿 바닥글 등에 고정된 **주관·운영 기관명**(예: ○○대학교 창업지원단)은 지원자 개인정보가 아니므로 템플릿대로 둔다. 지원자 소속이 드러나는지만 확인한다.
- 경쟁사는 공개 정보이므로 실명으로 비교하고 확인 경로(공식 안내·요금표·확인 시점)를 단다. 익명 비교표는 확인할 수 없어 근거로 인정받기 어렵다.
- 협력 기관·고객사는 실명이 증빙의 힘이므로, 공개 동의가 있거나 양식이 요구하면 실명으로 쓰고 아니면 '○○구청', 'A사'로 가린다.
